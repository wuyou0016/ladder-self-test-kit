# 一周自测计划

**目标**：在你自己的网络、你常用的时段里，用 7 天回答一个问题——它够不够稳？不是为了得到一个漂亮的数字。

## 开始前

1. 买**最低档月付**，不要为了测试买年付；
2. 打开 [`self-test-log-7days.csv`](self-test-log-7days.csv)；
3. 选一个固定的测试时段，**必须包含晚高峰**（大约 19:00–23:00）。

## 七天安排

| 天 | 做什么 |
| --- | --- |
| 第 1 天 | 确认能连、能用；记录客户端版本、协议、代理模式 |
| 第 2 天 | 晚高峰基线：连续使用 30 分钟，记录断线与卡顿 |
| 第 3 天 | 换时段对比：白天与晚高峰各测一次，看变慢是“全天”还是“只在晚高峰” |
| 第 4 天 | 用真实场景测：开会、玩游戏或看视频，凭体验记录（瞬移、断音、缓冲） |
| 第 5 天 | 同一地区换 2–3 个节点对比，排除“个别节点的问题” |
| 第 6 天 | 周末时段再测一次 |
| 第 7 天 | 汇总记录，按下面的方法做决定 |

## 怎么测数字

- **丢包率**：命令行 `ping -n 100 域名`（Windows）或 `ping -c 100 域名`（macOS / Linux），看最后统计里的“丢失 / packet loss”；
- **延迟**：看统计里的平均、最小、最大；最大和最小差得越多，抖动越大；
- **注意**：系统代理模式下 `ping` 往往**不会经过代理**（它用的是 ICMP）。要测节点本身，用客户端自带的延迟测试；要测“用起来怎么样”，用真实应用的体验记录。开启 TUN 模式后，结果才更接近经过代理的情况。

## 怎么读结果（经验判断，不是行业标准）

- **偶尔一次变差**：多半是临时波动，不必过度解读；
- **同一时段连续 3 天以上反复变差**：很可能是线路在该时段拥堵，这才需要认真对待；
- **所有节点同时变差**：先排查本地网络、客户端、系统时间，再怀疑服务商；
- **只有某个地区的节点差**：换同一家的其他地区节点；
- **体验问题很明显但数字正常**：以体验为准。

## 失败的判定

出现下面任意情况，建议不要续费，也不要买更长周期：

1. 你真正使用的场景下，问题**每天都出现**，且客服无法给出合理解释；
2. 退款规则不清楚，或者问到退款时回复含糊；
3. 价格或规则在购买后发生了未通知的变化。

通过的话也不要立刻买年付：先续一个月，同时保留备用方案。
